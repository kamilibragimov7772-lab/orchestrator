Версия: 1.1

> **Идентификаторы критериев (введены 2026-08-21, уточнены в тот же день).** Устойчивый ID есть
> у критериев ЧЕТЫРЁХ ОСЕЙ: `AR` — архитектура · `DC` — дизайн · `CN` — наполненность ·
> `UC` — юзабилити. Нумерация сквозная внутри оси: сначала high, затем medium, затем low.

> резолвилась в чужой пункт. Это опаснее отсутствия ID: раньше несуществующий ID был заметен,

> `ar_failed: [AR3, AR7]` резолвятся только против этого файла. Локальные копии таблиц
> критериев в карточках агентов — справочные; при расхождении истина здесь.
>
> Введено по итогам аудита определений: 7 агентов цитировали ID, которых в каноне не было,

## Зачем этот документ

«Хороший сайт» — формулировка, под которой каждый понимает своё. Дизайнер скажет «красиво». Маркетолог — «конвертит». Разработчик — «быстро грузится». Доступность-аудитор — «WCAG AA». Все правы, и все говорят про разное.

Этот документ собирает все эти «свои» в одну рамку из 4 осей плюс технический слой, и фиксирует измеримые критерии для каждой. Когда ревьюер пайплайна получает артефакт на проверку, он смотрит на этот файл и сверяется по чек-листу, а не по интуиции.

Это аналог `~/.claude/agents/_shared/budget_discipline.md` для бюджетного протокола — единый референс на который ссылаются все агенты-ревьюеры.

## Четыре оси «хорошего сайта»

### Ось 1. АРХИТЕКТУРА (information architecture)

Информационная архитектура — это ответ на вопрос «как пользователь находит то, что ему нужно». Плохая архитектура = пользователь уходит, не найдя.

#### Обязательные критерии (high severity — блокируют)

— **[AR1]** **Глубина sitemap ≤3 уровней** для сайта 10–30 страниц. Уровни считаются от главной. Главная (1) → услуги (2) → конкретная услуга (3). Если есть страницы на уровне 4 — это сигнал плохой группировки.

— **[AR2]** **Каждая страница reachable за ≤2 клика** с главной для ключевых пользовательских сценариев. Контактная страница — 1 клик. Страница услуги — 2 клика максимум. Если нужно 3+ — IA неоптимальна.

— **[AR3]** **Нет orphan-страниц** — страниц, на которые нет ни одной внутренней ссылки. Каждая страница присутствует либо в главной навигации, либо в footer, либо ссылается из связанной контентной страницы.

— **[AR4]** **URL читаемые, в kebab-case латиницей или транслитерацией**. `/services/dental-implants/` — да. `/services/?id=42` — нет. `/услуги/имплантация` — нет (кириллица в URL — постоянный источник багов с encoding).

— **[AR5]** **Mobile-first navigation**. Меню сначала проектируется под мобилу (гамбургер, drawer, accordion), потом масштабируется на десктоп. Не наоборот.

#### Важные критерии (medium severity — должны быть, но не блокируют запуск)

— **[AR6]** Breadcrumbs на страницах глубже 2 уровня.
— **[AR7]** Footer со структурной картой (3-5 колонок: услуги, компания, ресурсы, контакты).
— **[AR8]** Поиск (если страниц >25 или есть блог с >50 постов).
— **[AR9]** Канонические URL (`<link rel="canonical">`) на каждой странице.
— **[AR10]** Связанные страницы (related content blocks) на ключевых посадочных.

#### Желательные критерии (low severity)

— **[AR11]** XML sitemap с приоритетами и lastmod.
— **[AR12]** RSS-фид для блога.
— **[AR13]** hreflang для multi-language (если применимо).
— **[AR14]** Custom 404 страница с поиском и предложением альтернативных путей.

#### Методология ревью

Для оси «Архитектура» ревьюер опирается на:
- Abby Covert «How to Make Sense of Any Mess»
- Nielsen Norman Group articles по IA
- Card sorting и tree testing валидация (если проводилась)

### Ось 2. ДИЗАЙН (визуальный язык)

Дизайн — это не «красиво» (это субъективно), а «читается, навигируется, не отвлекает, узнаваемо как бренд».

#### Обязательные критерии (high severity)

— **[DC1]** **Контраст текста ≥4.5:1 для основного текста, ≥3:1 для крупного (≥18pt или ≥14pt bold)**. WCAG 2.2 AA. Проверяется через axe-core или вручную через WebAIM Contrast Checker.

— **[DC2]** **Type scale последовательная**. Размеры шрифта подчиняются единой шкале (Modular Scale 1.25/1.333/1.5 или Utopia fluid). Не 14px, 15px, 17px, 18px вразнобой.

— **[DC3]** **Шрифт основного текста поддерживает кириллицу полностью**. Не только базовый набор, но и ё, расширенный диапазон. Проверяется тестовым текстом «Привет Москва Йошкар-Ола Ёлка Съёмка» через визуальный осмотр.

— **[DC4]** **Цветовая палитра ≤7 цветов плюс нейтрали**. Brand primary, brand secondary (опционально), 2-3 semantic (success, warning, error, info), 4-5 нейтралей (от white до near-black). Если палитра больше — design system избыточна.

— **[DC5]** **Spacing система на 4px или 8px grid**. Все отступы кратны базе. 4, 8, 12, 16, 24, 32, 48, 64, 96. Не 13px, 17px, 22px.

— **[DC6]** **Состояния спроектированы для каждого интерактивного элемента**: default, hover, active, focus (видимый!), disabled, error, loading, empty. Если хотя бы одно состояние не описано в спеке — артефакт fail.

— **[DC7]** **Brand consistency**: логотип, цвета, типографика, тон голоса одинаковы на всех страницах. Не «домашняя в тёмном бренде, остальные в светлом».

— **[DC8]** **Motion respects prefers-reduced-motion**. Все анимации либо отключаются, либо упрощаются для пользователей с этим флагом. Не добавлено — fail.

— **[DC9]** **Длительность UI-анимаций 200–400ms**. Быстрее воспринимается как баг (мерцание), медленнее — утомляет. Hero-анимации до 600ms. Дольше — фейл.

#### Важные критерии (medium severity)

— **[DC10]** Visual hierarchy: hero → secondary → tertiary читается за 2 секунды беглого взгляда.
— **[DC11]** Z-pattern или F-pattern для контентных блоков.
— **[DC12]** Поддержка dark mode через CSS variables (если в design system заложена).
— **[DC13]** Иконки из единого набора (Lucide, Heroicons, Phosphor) — не микс.
— **[DC14]** Изображения с consistent treatment (фильтры, скругления, рамки).

#### Желательные критерии (low severity)

— **[DC15]** Variable fonts (один файл, все веса) для экономии.
— **[DC16]** Иллюстрации единого стиля (если используются).
— **[DC17]** Skeleton screens для loading-состояний.
— **[DC18]** Микровзаимодействия на ключевых CTA.

#### Методология ревью

Для оси «Дизайн» ревьюер опирается на:
- Atomic Design (Brad Frost)
- Design Tokens W3C draft
- WCAG 2.2 AA для контраста
- Material Motion + Apple HIG для motion
- Robert Bringhurst «Elements of Typographic Style» для типо-канона

### Ось 3. НАПОЛНЕННОСТЬ (контент, копирайтинг, SEO)

Контент — это то, ради чего пользователь пришёл. Сайт без контента = красивый макет без смысла.

#### Обязательные критерии (high severity)

— **[CN1]** **Один H1 на страницу, иерархия H2 → H3 без пропусков**. Структура заголовков отражает структуру контента. Не «H1, потом сразу H4» — нарушает SEO и screen reader навигацию.

— **[CN2]** **Meta-title ≤60 символов, meta-description ≤160 символов**, уникальные на каждой странице. Не дублируются.

— **[CN3]** **Каждая страница имеет TL;DR или явный value proposition в первом экране**. Пользователь за 5 секунд понимает «что это и зачем мне».

— **[CN4]** **CTA конкретны и измеримы**. «Запишитесь на консультацию» — да. «Связаться» — нет (что значит — позвонить, написать?). «Узнать больше» — нет (что узнать?).

— **[CN5]** **Все изображения с alt-текстами на русском**, описывающими содержимое или функцию. Не «image1.jpg», не пустые alt у не-декоративных картинок.

— **[CN6]** **Тон голоса единый и определён в `tone_of_voice.md`**. Все тексты сайта проверяются по этому канону. Не «домашняя — формальная, услуги — фамильярные».

— **[CN7]** **Ссылки описательные**, а не «нажмите здесь», «подробнее». Текст ссылки — самостоятельный смысл. WCAG требование.

— **[CN8]** **Schema.org JSON-LD как минимум для Organization и одной из: Service, Product, Article, LocalBusiness**. Без structured data — нет rich snippets в Google.

— **[CN9]** **Open Graph + Twitter Card теги** на каждой странице. Заголовок, описание, изображение 1200×630 для OG.

#### Важные критерии (medium severity)

— **[CN10]** Внутренние ссылки между связанными страницами (минимум 2-3 на странице услуги).
— **[CN11]** Контактная информация в нескольких местах: header, footer, контактная страница, schema.org.
— **[CN12]** Privacy policy и условия использования (для русской аудитории — соответствие 152-ФЗ).
— **[CN13]** Cookie consent (если есть аналитика или маркетинговые скрипты).
— **[CN14]** Микроразметка Breadcrumbs (BreadcrumbList schema).

#### Желательные критерии (low severity)

— **[CN15]** FAQ-блоки с FAQPage schema (триггерят rich snippets).
— **[CN16]** Author schema для блог-постов (E-E-A-T).
— **[CN17]** LocalBusiness schema с координатами и часами работы (если бизнес физический).
— **[CN18]** Social proof (отзывы, кейсы, цифры) на ключевых посадочных.

#### Методология ревью

Для оси «Наполненность» ревьюер опирается на:
- Torrey Podmajersky «Strategic Writing for UX» (Microsoft)
- Smashing Magazine UX Writing series
- HubSpot/Ahrefs SEO content frameworks
- schema.org официальная документация
- Google Rich Results Test

### Ось 4. ЮЗАБИЛИТИ (UX, удобство использования)

Юзабилити — это пересечение архитектуры, дизайна и наполненности на стороне пользователя. «Я могу сделать то, зачем пришёл, легко и без раздражения».

#### Обязательные критерии (high severity)

— **[UC1]** **Mobile responsive 320px – 1920px**. Сайт корректно отображается на всём диапазоне без горизонтального скролла. Базовые брейкпоинты: 320, 768, 1024, 1440, 1920.

— **[UC2]** **Touch targets ≥44×44 px** на мобильной версии. Apple HIG / Material Design стандарт. Маленькие кнопки на мобиле = промахи.

— **[UC3]** **Lighthouse Performance ≥90**, Accessibility ≥95, Best Practices ≥95, SEO ≥95 на мобильной симуляции (default Lighthouse settings). На production против live URL — Performance ≥85 (учитывая хостинг и сеть).

— **[UC4]** **Core Web Vitals 2026**: LCP <2.5s, INP <200ms, CLS <0.1. Если хоть один показатель «poor» — fail.

— **[UC5]** **Axe-core: 0 critical и serious violations**. Moderate допустимы единичные с обоснованием. Minor — не блокирует.

— **[UC6]** **Клавиатурная навигация**: все интерактивные элементы доступны через Tab, focus visible (видимый focus ring), порядок логичный. Не «кликнул через Tab — focus улетел в footer, потом вернулся в header».

— **[UC7]** **Формы**: inline validation, ошибки рядом с полем (не общим списком сверху), submission feedback (что отправлено), aria-required и aria-invalid правильно проставлены.

— **[UC8]** **Loading states / empty states / error states спроектированы**. Не «белый экран пока грузится», не «пустой блок если данных нет», не «непонятная ошибка если что-то упало».

#### Важные критерии (medium severity)

— **[UC9]** Скорость на медленной 3G (Lighthouse throttling): сайт остаётся usable за <5 сек до first interaction.
— **[UC10]** Offline-fallback (через service worker) для ключевых страниц — желательно для корпоративных сайтов.
— **[UC11]** Skip-to-content link для screen reader пользователей.
— **[UC12]** Aria-labels на нестандартных интерактивных элементах (toggles, dropdowns, modals).
— **[UC13]** Поддержка screen reader (VoiceOver / NVDA): manual проверка ключевых сценариев.

#### Желательные критерии (low severity)

— **[UC14]** Reduced data mode (prefers-reduced-data) — облегчённые ассеты для slow networks.
— **[UC15]** Contrast preference (prefers-contrast) — увеличенный контраст для пользователей с low vision.
— **[UC16]** Auto-save в формах с многошаговым вводом.
— **[UC17]** Smart defaults в формах (текущий город, инкрементальные подсказки).

#### Методология ревью

Для оси «Юзабилити» ревьюер опирается на:
- Nielsen 10 Usability Heuristics (1994/2024 update)
- WCAG 2.2 AA полный (axe-core + manual)
- Core Web Vitals 2026 standard
- Apple Human Interface Guidelines (Mobile Accessibility)
- Material Design Accessibility guidelines

## Технический слой (cross-cutting)

Технический слой не отдельная ось «хорошего сайта», но он пронизывает всё. Каждый из этих пунктов проверяется специализированным аудитором.

### Performance (`performance-auditor`)

Тулинг: Lighthouse CLI через Bash.

Threshold:
- LCP <2.5s (good), <4.0s (needs improvement), >4.0s (poor — fail)
- INP <200ms (good), <500ms (needs improvement), >500ms (poor — fail)
- CLS <0.1 (good), <0.25 (needs improvement), >0.25 (poor — fail)
- Total Blocking Time <200ms (mobile)
- Speed Index <3.4s (mobile)

Команда:
```bash
npx lighthouse <url> --preset=desktop --output=json --output-path=./perf.json
```

### Accessibility (`accessibility-auditor`)

Тулинг: axe-core CLI / Pa11y через Bash.

Threshold:
- 0 critical violations
- 0 serious violations
- moderate <5 (с обоснованием)
- WCAG 2.2 AA compliance

Команда:
```bash
npx @axe-core/cli <url> --tags wcag22aa
```

Плюс manual review screen reader навигации по 5 ключевым сценариям.

### Security (`security-auditor`)

Тулинг: curl, npm audit, securityheaders.com API.

Обязательные headers:
- Content-Security-Policy (with unsafe-inline только если обоснован)
- Strict-Transport-Security (max-age=31536000; includeSubDomains)
- X-Frame-Options: DENY
- X-Content-Type-Options: nosniff
- Referrer-Policy: strict-origin-when-cross-origin
- Permissions-Policy: с явным запретом ненужных API

Минимум A на securityheaders.com.

Dependency audit:
```bash
npm audit --omit=dev --audit-level=moderate
```
Не должно быть high или critical уязвимостей.

Дополнительно:
- security.txt по `/.well-known/security.txt`
- Privacy policy и cookie consent (152-ФЗ если RU)
- TLS 1.3 only (или 1.2 минимум)

### SEO (`seo-auditor`)

Тулинг: curl + jsonld validator + Google Rich Results Test API.

Threshold:
- sitemap.xml существует, валиден, отдан Google Search Console
- robots.txt существует и не блокирует случайно ничего важного
- Все страницы имеют meta-title, meta-description, canonical
- OG-теги на всех страницах
- JSON-LD валиден через Google Rich Results Test
- Lighthouse SEO score ≥95
- hreflang при многоязычности

## Severity градация: блокеры vs не-блокеры

Каждый пункт критериев имеет severity. Ревьюер при выдаче critique помечает каждый найденный issue:

**HIGH (блокер).** Артефакт не может быть принят, пока issue не исправлен. Verdict ревьюера: **fail**.

**MEDIUM (важное, но не блокер).** Артефакт может быть принят с verdict **conditional-pass** при условии, что issue зафиксирован в backlog и будет исправлен до запуска (фаза 7).

**LOW (nice-to-have).** Артефакт принят (**pass**), issue идёт в backlog как improvement, не блокирует.

Ревьюер не может пометить пункт как HIGH, если он не отнесён к HIGH в этом документе. **Исключение — технический слой:** его пороги здесь без severity-меток, severity определяется карточкой соответствующего аудитора (она же владеет каталогом `PA*`/`AA*`/`SC*`/`SE*`). Это защита от завышения требований ревьюером по своей инициативе.

## Как ревьюер использует этот документ

Алгоритм ревью одного артефакта:

1. **Прочитать артефакт целиком**.
2. **Прочитать этот файл** (`site_quality_definition.md`) и `critique_format.md`.
3. **Для каждой оси, релевантной фазе** (см. ниже), пройтись по чек-листу.
4. **Зафиксировать issues** с severity и привязкой к пункту критериев.
5. **Зафиксировать что прошло** (раздел «What passed») — это важно, ревью без явного approval тоже плохо.
6. **Вынести verdict**: pass / conditional-pass / fail.
7. **Сформулировать recommendations** для автора, если verdict не pass.
8. **Сохранить critique** в `<phase>/critique_v<N>.md`.
9. **Вернуть оркестратору**: путь к critique + verdict + 1 строкой главное.

## Версионирование и эволюция

Этот документ — живой. Каждое обновление:
- увеличивает версию в frontmatter (1.0 → 1.1 для добавления критериев, 2.0 для пересмотра философии)
- фиксируется в decision-log пользователя (`<VAULT_ROOT>/11-Decisions-Log/<date>.md`)
- ссылается на конкретный pain point из реальных прогонов («после прогона X выяснилось, что критерий Y слишком мягкий»)

Все ревьюеры в critique-файле указывают `quality_definition_version: <version>` — это позволяет понять «по каким критериям был выдан этот critique».
