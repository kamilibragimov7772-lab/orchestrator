# /harness-audit

Прогон harness-optimizer'а по моему персональному стеку Claude Code.

## Что делать

1. Парсинг `$ARGUMENTS`:
   - Пусто или `full` → scope: full
   - `agents` / `commands` / `memory` / `orchestr` → этот scope только
   - Иначе → spросить меня одно уточнение

2. Запусти Task → `harness-optimizer` с параметрами:
   - scope: <вычисленный>
   - путь сохранения: `<VAULT_ROOT>\08-Работа-Claude\_harness_audit\<YYYY-MM-DD>_audit.md`
   - bucket: standard

3. Когда harness-optimizer закончит — прочитай результат целиком (короткий, по факту).

4. Покажи мне сводку (≤250 слов):
   - Сколько единиц проверено, сколько P0 / P1 / P2
   - Топ-5 самых жирных находок (с категорией KEEP/RENAME/MERGE/RETIRE/FIX)
   - Roadmap первых 3 шагов (что я могу сделать прямо сейчас)
   - Открытые вопросы (если есть)

5. Спроси меню — что делать дальше:
   - **A** — применить первые 3 правки прямо сейчас (через site-editor / руками)
   - **B** — отложить в OpenClaw task
   - **C** — только сохранить отчёт, обсудим позже

## Параллельность

Если аудит за тот же день уже существует (`_harness_audit/<date>_audit.md`) — открой его, не пересобирай. Скажи пользователю «уже собрано сегодня, обновить?».

## RETIRE-ритуал (обязательно)

Каждый прогон harness-audit ОБЯЗАН предложить минимум 1 кандидата на RETIRE (агент/команда/правило к выводу из эксплуатации) — либо явно обосновать в отчёте, почему ни одного кандидата нет. Стек, который только растёт, — технический долг. Цель ритуала — не дать стеку распухать.

## Применяется когда

- Раз в 2-4 недели как профилактика (по моей инициативе тоже)
- После добавления 3+ новых агентов / команд / правил
- После того, как я заметил конфликт или dead-end в стеке
- Перед большой реструктуризацией (например смена оркестраторской философии)

## Примеры

- `/harness-audit` → полный
- `/harness-audit agents` → только агенты
- `/harness-audit memory` → только MEMORY.md и связанные файлы
