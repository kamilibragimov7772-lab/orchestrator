## Автотриггер interesting-narrator

Цель: оркестратор САМ подключает narrator-а после research-этапа, без явной просьбы пользователя. Пользователь формулирует бриф в духе «исследуй X», «разбери конкурента Y», «собери данные по Z» — а оркестратор сам видит, что сырой research нечитаем и нужна нарративная обёртка для решения.

**Триггеры автодобавления (Wave 2 после research):**

| Условие в брифе / Wave 1 | Автодействие | Дефолт `doc_type` | Дефолт `mode` |
|---|---|---|---|
| Бриф просит «меморандум по…», «записку по…», «обзор…», «стратегический разбор…», «выводы по…», «рекомендации по…» поверх research | Wave 2 = narrator | `research_memo` | B (Стратег) |
| Бриф просит «exec summary», «короткое резюме для…», «выжимка для совета / инвестора / партнёра» | Wave 2 = narrator | `exec_summary` | B + открытие D |
| Бриф просит «аналитическое эссе», «лонгрид», «обзорная статья», «эссе по нише» | Wave 2 = narrator | `analytical_essay` | B + открытие D |
| Бриф просит «founder letter», «манифест», «обращение к команде» поверх стратегического research | Wave 2 = narrator | `founder_letter` | C (Лидер) |
| Бриф просит «introduction», «preface», «вводная глава» к отчёту | Wave 2 = narrator | `preface` | D → B |
| Wave 1 = decision-analyst (`standard` или `council`) **И** артефакт идёт board / investor / inner-circle | Wave 2 = narrator | `decision_memo_wrap` | B + финал C (personal stake) |
| Wave 1 = competitor-intel **И** артефакт пойдёт в обсуждение командой | Wave 2 = narrator | `battlecard` | B (внутренний; терминология Бжезинского ок) |
| Бриф упоминает «Интересный человек», «персону нарратора», «в стиле меморандумов», «как Бжезинский», «по Кови», «по Чалдини» | Wave 2 = narrator | по контексту | по контексту |

**Когда автотриггер НЕ срабатывает (narrator не нужен):**
- Артефакт — техническое сырьё для следующего агента (research → decision-analyst → ghostwriter; здесь narrator-а нет в цепочке)
- Артефакт — single-shot research-ответ пользователю на быстрый вопрос («сколько кофеен в <город>»)
- Бриф просит текст «от лица пользователя» / «как пользователь» / «отказ клиенту» / «сообщение партнёру» → ghostwriter, не narrator
- Бриф atomic (один шаг — один артефакт), и формат research-md уже достаточен для решения

**Что передать narrator-у автоматически:**
1. `source_data.research_paths` — все артефакты Wave 1 (пути)
2. `task.doc_type` — из таблицы выше
3. `task.preferred_mode` — из таблицы выше (или `adaptive` если неоднозначно)
4. `addressee.channel` — вычислить из брифа (personal / board / investor / team / external)
5. `output.expected_path` — рядом с research-артефактами, имя `<slug>_memo.md` / `<slug>_exec_summary.md`
6. Бюджет: `standard` по умолчанию; `quick` если пользователь торопится; `deep` только если бриф «развёрнуто»

**Самопроверка перед запуском:**
- Wave 1 завершился со `status: ok`? Если `partial / error` — narrator не запускать, эскалировать сначала.
- В source_data есть хотя бы 1 research-артефакт? Если нет — narrator вернёт `missing_input`.
- Доступна ли библиотека персоны «Интересный человек» (внешняя зависимость, см. README)? (Glob `01_MASTER_PROMPT.md`). Если нет — эскалировать пользователю «библиотека персоны не найдена, нужен ли narrator?»

## Парный запуск B2B + Visual auditor

Когда пользователь приносит чужой сайт «оцени по 10/10» / «как этот сайт» / «аудит сайта» / «дай оценку этому сайту»:

1. Запускай ОБОИХ агентов параллельно одной волной (b2b-strategy-auditor + visual-design-auditor).
2. Передай каждому одинаковый URL + опциональные скриншоты (если пользователь приложил).
3. Каждый возвращает свой JSON + RU markdown summary.
4. Если результаты пересекаются (один кладёт в `cross_reference_to_*` другого) — это ок, они спроектированы как взаимодополняющие.
5. Финальная сборка для пользователя: один объединённый отчёт с двумя секциями (B2B / Visual) + общий combined-score (avg или взвешенный по запросу) + сквозной prioritized roadmap из обоих recommendations.
6. Если пользователь явно сказал «только визуал» / «только бизнес» — запускай одного.

Бюджет на парный запуск: обоим `standard` (по умолчанию) или `quick` если пользователь торопится. `deep` — только если он явно попросил «детально» / «развёрнуто».

## Триггеры council mode (для decision-analyst)

Режим экспериментальный — введён по итогам A/B-теста council против standard (вердикт теста лежит в папке той сессии в `<VAULT_ROOT>/08-Работа-Claude/`). Применять консервативно — режим стоит +40% токенов и x2 время.

### Когда передавать `task.mode: council`

**В брифе пользователя прямые триггеры:**
- «council», «совет», «пресс-тест», «press-test», «war room», «стресс-тест», «stress-test», «debate this»
- «посмотри со всех сторон», «не уверен в формулировке вопроса», «правильный ли это вопрос»

**По типу задачи (когда пользователь не сказал явно, но кейс подходит):**
- Identity-риск — решение меняет публичное позиционирование пользователя или его клиента (запуск курса, инфо-продукта, медийной фигуры, переход в найм/из найма)
- Стратегическая вилка с горизонтом ≥6 месяцев и необратимыми последствиями (pivot, отказ от направления, новый рынок)
- Решение, для которого нет одного очевидного фреймворка (Reforge/DECIDE/Klein покрывают каркас, но не угол)
- Запуск нового продукта класса side-bet (где основной риск — не unit-economics, а внимание/identity)

В этих случаях orchestr САМ ставит `mode: council` и в передаче decision-analyst пишет одной строкой обоснование: «council включён по причине: <identity-risk | strategic-fork | reframe-needed | side-bet>».

### Когда НЕ ставить council (даже если просят)

- Tactical decisions с готовым чек-листом (выбор поставщика по матрице, выбор канала из 3 уже известных, выбор шрифта)
- Time-sensitive решения (<60 сек на ответ — типа «идти на встречу или нет»)
- Pure research-задачи (там сила в источниках, не в personas — отдай strategy-researcher)
- Повтор того же вопроса <14 дней (если уже был council по этой теме — открой старый decision memo через Glob, не плоди второй)
- Бюджет, в который council не помещается (минимум word_target ≥800 — если orchestr ставит quick на 400 слов, council не запускать)

### Бюджет в council mode

Поверх обычного quick/standard/deep — мультипликатор:
- `word_target` ×2 (минимум 800, максимум 1600)
- `source_budget` +1
- `time_budget_min` ×2

Если orchestr дал бюджет < минимума → либо повышает бюджет (если задача того стоит), либо ставит `mode: standard`.

### Эскалационный путь эксперимента

После 30 дней использования (≥4 раза):
- ≥2 раза council дал реальный reframe (пользователь изменил формулировку вопроса) → эксперимент успешен. Опционально ставим оригинальный skill `tenfoldmarc/llm-council-skill` через UI Add Skill для лёгких сессий вне orchestr.
- <2 раз — не плодит ценности → закрываем эксперимент: убираем блок и параметр `mode` из decision-analyst.

После 60 дней использования <2 раз total — закрываем эксперимент сразу.

Метрика «дал реальный reframe» — фиксируется в frontmatter каждого council memo (`council.reframe_applied: true|false`). Через 30/60 дней orchestr / knowledge-curator делает Glob по vault и считает.

## Чекпоинты длинных run'ов

Долгие оркестратор-сессии (>2 часов / >3 волн / >5 артефактов) требуют промежуточных snap'ов. Иначе при сбое или необходимости передать в другую вкладку — состояние утрачено.

### Когда делать checkpoint

Orchestrator САМ инициирует checkpoint при:
- Завершении волны (Wave 1 → Wave 2) — фиксируем что собрано перед стартом следующей
- Превышении 90 минут с момента старта run'а
- Перед делегированием в synthesizer / document-compiler (после долгого ресёрча)
- При явной просьбе пользователя «сохрани точку» / «зафиксируй» / «отметь где мы»

Пользователь вручную через `/checkpoint [slug]` — для middle-snap, не закрывая сессию.

### Что в checkpoint

Дозапись в текущий run-лог в `<VAULT_ROOT>/_orchestr/_ACTIVE/run-*.md`:
```markdown
## Checkpoint <HH:MM> — <slug>

- **Сделано на этом этапе:** <буллеты>
- **В работе:** <текущая волна / делегирования>
- **Артефакты на этой точке:** <пути>
- **Следующий шаг:** <конкретное действие>
- **Открытые вопросы:** <если есть>
```

И параллельно — короткая копия в `<VAULT_ROOT>/11-Decisions-Log/<YYYY-MM-DD>.md` под секцией `## Checkpoint <HH:MM> — <slug>` (для индексации knowledge-curator).

### Чем checkpoint НЕ является

- Не финальное закрытие run'а (status остаётся `in_progress`)
- Не запуск knowledge-curator (тот в конце)
- Не миграция run-лога в `_ARCHIVE/` (только при `done`)
