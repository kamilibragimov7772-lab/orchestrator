# Проверка работоспособности стека

Два готовых промпта: быстрый — семь агентов сквозной цепочкой за один прогон, полный — каждая из 41 карточки получает микро-задачу на один вызов. Оба вставляются в Claude Code как есть. Все данные в задачах вымышленные; никаких ссылок на реальные проекты.

**Оговорка про стоимость.** Проверка тратит токены: быстрая — один прогон на 7 агентов (по опыту ~20 минут), полная — 41 вызов плюс сборка сайта с `npm`. Все бюджеты — пресет `quick`, кроме тех мест, где карточка требует иного (отмечено). Site-build в полной проверке — самая дорогая часть; если сайты не строишь, пропусти волны S1–S12.

**Что считается результатом.** Не «агент ответил», а: вернулся по контракту (`status`, `artifact.path`, `summary`, `budget_used`), артефакт открывается повторным `Read`, содержимое отвечает критерию PASS из таблицы. Отказ по воротам входа (`missing_input`, `tool_unavailable`) при реально отсутствующем входе — это PASS ворот, а не провал агента; отмечается отдельно.

## 1. Быстрая проверка (~20 минут)

```text
Задача условная, все данные вымышленные. Кофейня «Зерно»: одна точка в спальном районе города-миллионника, 40 чеков в день, средний чек 350 ₽, два бариста, кухня ограничена сэндвичами и выпечкой. Файл с этой же таблицей сохрани рядом с run-логом как EVAL_QUICK.md и добавь путь в artifacts.
```

Что должно получиться: run-лог в `<VAULT_ROOT>/_orchestr/_ARCHIVE/` со `status: done`, семью зелёными проверками валидатора, полями `obraz_gotovogo: filled` и `priyomka: <вердикт>`; секция `## Приёмка`, дописанная приёмщиком; артефакты — ТЗ, ресёрч, memo, сообщение, отчёт voice-checker, `EVAL_QUICK.md`. ### 2.3 Пять контрольных вопросов для самооценки стека

Ответ «да» без доказательства не принимается: рядом с каждым — команда, код возврата или цитата из лога.

1. **Enforcement на старте сработал?** В run-логе есть строка Шага 0 с результатом линта карточек (`agent-lint.py --quiet`, число ошибок), реконсиляции архива и индекса, счётчика образа готового (`gotovo-counter.py`, строка-сводка). Нет строки — Шаг 0 пропущен, и остальная проверка мерит не стек, а везение.
2. **Приёмщик отказался судить неполный комплект?** Второй вызов `/priyomka` на прогоне со `status: planning` вернул «не подлежит приёмке» (код 4 от `checks.py`) и не начал работу; `final-quality-gate` на комплекте без одного отчёта отказался агрегировать. Судил — значит приёмка вырождается во вкусовщину.
3. **Линтер зелёный — и краснеет там, где должен?** `agent-lint.py --quiet` → «ОШИБОК: 0» на установленном дереве. И тут же мутант: копия любой карточки без `Bash` в `tools:` при «посчитай …» в теле → ошибка. Зелень без красного мутанта ничего не значит.
4. **Валидатор закрытия не пропустил пустой `artifacts:`?** Подсади дефект: перед закрытием оставь `artifacts: []` при путях в теле лога. Оркестратор обязан перенести пути в поле (проверка 2 валидатора), а не закрыть прогон. `checks.py` на таком логе — код 1 «нечего принимать».
5. **Мутационная проверка покраснела на подсаженном дефекте?** `python-build-engineer` приложил лог мутанта с красным тестом; `checks.py` на run-логе, где один путь в `artifacts:` заменён на несуществующий, вернул код 1 и назвал путь. Проверка, которая не краснеет на сломанном, не проверяет ничего — чинить её, а не выводы по ней.

Быстрая проверка отвечает на вопрос «стек собран и цепочка проходит». Полная — «каждая карточка исполнима на моей машине с моими зависимостями». Пять вопросов — «стек проверяет сам себя, а не только объявляет». Повторять полную проверку имеет смысл после правок протокола, контрактов в `_shared/` или переезда на другую машину; быструю — после любой правки карточек ядра.
